# ProcMesh V1.1 总体架构设计

日期：2026-08-16  
状态：待用户审阅  
范围：V1.1（Q1–Q5）。不含 V1.2。不改写 V1.0 合同，只增量。

本文是实现合同，不是 PRD 摘抄。产品原则与故障语义以 `docs/v2-prd/v2-prd.md` 为准；V1.0 已锁边界以 `docs/superpowers/specs/2026-08-13-v1-mvp-architecture-design.md` 为准。本文锁定 V1.1 的权威落点、组件增量、读路径、阶段切分和测试门槛。

**不要从本文直接写代码。** 与 V1.0 相同：先有总体 spec，再按 Q1–Q5 **各写一份**实施计划，一阶段验收通过再开下一阶段。

## 1. 背景与目标

V1.0 已交付：本机进程平面、ConnectRPC/CLI、Gossip 身份、mTLS Write-to-Owner、Raft 用户/RBAC/准入、嵌入式 Vue。Raft 不存 `agent_groups` / `alert_channels`；RBAC 只有 `CLUSTER` 与 `AGENT`；指标只有 5 秒即时快照。

V1.1 成功标准：

1. Agent Group 强一致可管；Process Group 仍是 Owner spec 字符串；RBAC 可按组授权（PRD §18 的 V1.0 刻意缺口补上）。
2. 任意入口可发起 Batch，部分成功可见，Case 7 可脚本化验收。
3. 进程/本机告警由 Owner 发，集群级告警由 Raft Leader 发；Web + Webhook + Email + 企业微信 + 钉钉 + Slack 均可投递。
4. Owner 保留 7 天本地历史（现有 5 条序列），详情页可画趋势。
5. Spec 可备份到 Filesystem / S3 Compatible / Peer，恢复只走 Owner `ApplySpec` + CAS。
6. 不引入中心管理 Server，不把 Gossip 当成事务，不把运行时写进 Raft。

非目标（沿用 PRD §91 与 V1.2）：

- 跨节点调度、自动 Placement、故障迁移、跨节点依赖
- Exactly Once Batch、Exactly Once Alert
- Process Group 注册表、嵌套组、label selector 推导组成员
- 集群时序库、Network/Load/FD/IO 采集
- 证书轮换、MFA、升级编排（V1.2）
- 默认开启任意命令执行
- Windows

整集群配置备份与 Peer 灾备副本不再属于 V1.1 非目标。该能力是 Q5 本地配置备份之后的增量边界，权威合同见 `docs/superpowers/specs/2026-08-19-cluster-backup-disaster-replication-design.md`，实施计划见 `docs/superpowers/plans/2026-08-19-cluster-backup-implementation.md` 与 `docs/superpowers/plans/2026-08-20-cluster-backup-completion.md`。Owner `ApplySpec` + `expected_revision` CAS、Raft 只存控制面元数据、Gossip 只传摘要、以及 mTLS Write-to-Owner 约束不变。

## 2. 已锁定约束

| 项 | 决定 |
|----|------|
| 交付形态 | 一份 V1.1 总体 spec；实现按 Q1–Q5 分阶段，每阶段一份 plan |
| 一致性模型 | 不换。Local Authority + Gossip Summary + Direct RPC + Raft 控制面 |
| 二进制 / 端口 / 栈 | 与 V1.0 相同。不增加第四个管理 socket，不增加第二套 REST 资源模型 |
| Process Group | **不是** Raft 对象。权威是 Owner `ProcessSpec.Group` 字符串 |
| Agent Group | Raft 命名对象 + 显式 `node_id` 成员列表；一节点可多组 |
| Batch | 创建它的**入口 Agent**本地对象；后台扇出；禁止进 Raft / Gossip |
| Alert 配置 | `alert_channels` 与阈值/去重策略进 Raft |
| Alert 实例 | 发送者本地。Owner 发进程/本机；Leader 发集群级 |
| 历史指标 | Owner 本地；1 分钟点保留 24h，之后降为 5 分钟点至第 7 天；只覆盖现有 5 序列 |
| 备份 | FS + S3 + Peer 都验收；副本不是 writer；restore = Owner `ApplySpec` 新 revision |
| 读任意节点 | 控制面读本地 Raft；Batch 问原入口；Alert / 历史 / 备份目录按需 RPC，失败标 STALE |
| 协议 | `version.Protocol` 保持 `1`。Gossip JSON 加字段，旧节点忽略未知键。新 RPC 打到 V1.0 节点时对该调用返回 `UNAVAILABLE`，不把整个集群标 `INCOMPATIBLE_VERSION` |
| 平台 | 仍是 Linux 生产保证面；macOS 开发辅助 |

与 PRD 的刻意对齐/差异：

1. PRD §12 只列了 `agent_groups`，未列 `process_groups`。V1.1 不把 Process Group 做成控制面实体（消解 §12 与 §18/§89 的张力）。
2. PRD §89 的 Advanced Dashboard = 旧页增强 + Groups/Batches/Alerts/Backup 新页，不做独立大屏产品。
3. 备份不做额外载荷加密（Peer 走 mTLS，S3 走 HTTPS，FS 文件 0600）。整集群配置备份与 Peer 灾备副本按后续增量 spec 交付，不改写 Owner / Raft / Gossip / Restore CAS 约束。

## 3. 系统结构

V1.0 平面划分不变。V1.1 只往现有 Agent 进程里加包与服务：

```text
Browser / CLI
      │
      ▼
Any Agent :18680
      │
      ├── Cluster Control (Raft :18685)
      │     users / RBAC / 准入 / CRL
      │     + agent_groups
      │     + alert_channels / alert_policy
      ├── Gossip (:18689)
      │     membership + summary
      │     + ProcessSummary.group
      │     + ProcessSummary.process_id
      ├── Direct RPC mTLS (:18683)
      │     Write-to-Owner（进程/backup restore/history 读）
      │     入口本地：Batch worker 扇出
      └── Local SQLite
            V1.0 表
            + batches / batch_targets
            + alerts
            + metric_samples
            + backup_index（本机与已推 Peer 的元数据）
```

新包：

| 包 | 职责 | 允许依赖 |
|----|------|----------|
| `internal/batch` | 任务存储、展开、worker、重试 | `store`、`auth`、`rpc`、`control`（只读组成员） |
| `internal/alert` | 判定、fingerprint 去重、通道发送 | `store`、`control`（读通道配置）、`metrics` |
| `internal/backup` | Snapshot、Sink、Restore 编排 | `store`、`process`（ApplySpec）、`rpc` |
| `internal/metrics` | 扩展：1 分钟聚合、降采样、查询 | 不得 import `cluster` / `control` |

依赖方向仍遵守 V1.0：`process` 不得 import `cluster` 或 `control`。`batch` / `alert` / `backup` 可由 `api` 与 `agent` 编排，不得让 `process` 反过来依赖它们。

## 4. 数据权威

| 数据 | 权威 | 一致性 | 载体 |
|------|------|--------|------|
| Process Spec / Desired / Runtime / Logs / 明细 Metrics / 7 天历史 | Owner | 本地强一致 | SQLite + 文件 |
| Process `group` 字符串 | Owner（spec 字段） | 本地权威；集群视图最终一致 | spec + Gossip |
| Process / Agent / revision / group 名 / process_id 摘要 | Owner 产出 | 最终一致 | Gossip LocalState（不是 NodeMeta） |
| Users / Roles / Bindings / Agent Groups / Alert Channels / 策略 / 准入 / CRL | Cluster Control | 强一致 | Raft FSM + bbolt |
| Batch 任务与每 target 结果 | 创建该 batch 的入口 Agent | 本地 | 入口 SQLite |
| Alert 实例 | 发送者（Owner 或当时 Leader） | 本地 | 发送者 SQLite |
| Backup 副本 | 只读副本 | 本地文件 / S3 / Peer `backup/` | `BackupSink` |
| 入口 Audit / 执行 Audit | 入口 / Owner | 本地 | SQLite（不变） |

**Raft 仍禁止写入：** 进程 runtime、logs、即时或历史 metrics、batch 记录、alert 实例、process group 注册表、backup 载荷。

**Gossip 仍禁止携带：** mutation、batch 进度、alert 实例、backup 载荷、RBAC。

## 5. Agent Group、Process Group、RBAC

### 5.1 Agent Group

Raft 对象：

```text
AgentGroup
  group_id          UUID，创建时生成，不复用
  name              集群内唯一，1–64 字符，[A-Za-z0-9._-]，大小写敏感
  description       可选，≤256
  member_node_ids   显式列表，可空
  created_unix
  updated_unix
```

Raft 命令：`group_put`、`group_delete`、`group_member_add`、`group_member_remove`。  
权限：`node.manage`（内置 Cluster Admin / Super Admin）。读：`node.read`。

约束：

- 一个 `node_id` 可属于多个组。
- 只能加入已 `ADMITTED` 且未吊销的成员。未知 `node_id` → `INVALID`。
- `group_delete`：若仍有 `Binding.Scope == AGENT_GROUP && ScopeID == group_id`，拒绝（`CONFLICT`）。通过后原子删组并清空成员。
- `CmdMemberRemove` / revoke 在同一 FSM apply 路径把该 `node_id` 从所有组摘掉。
- 组成员**不以 Gossip 为准**。Node API 的 `agent_group_ids` 从本地 Raft 填。

### 5.2 Process Group

- 权威字段：已有 `ProcessSpec.Group`（及 proto `Process.group`）。
- 不预注册、不进 Raft、无 `GroupService` 对 Process Group 的 CRUD。
- 空字符串或未设 = 未分组。非空：trim 后 1–64 字符，允许字母数字、`.` `_` `-`，大小写敏感。非法值在 `ValidateSpec` / `ApplySpec` 拒绝（`INVALID`）。
- 改组名 = 改 spec：必须 `expected_revision`，产生新 revision。
- Gossip `ProcessSummary` 增加：
  - `process_id`（稳定身份）
  - `group`（可能为空）
- 集群「有哪些 process group 名」= 聚合各节点 Gossip。STALE 节点的名字可能过期。
- Grant `PROCESS_GROUP` 时 `scope_id` 是**名字字符串**，即使当前没有任何进程使用该名字。

Batch / 列表按 Process Group 选 target 时：Gossip 只做初筛；**执行前必须 RPC 读 Owner spec** 核对 `group`。对不上的 target 记入结果（例如 `INVALID` / 跳过原因），不得静默丢掉。

### 5.3 RBAC Scope

`control.ScopeType` 增加：

| Scope | ScopeID | 命中 |
|-------|---------|------|
| `CLUSTER` | （空） | 全部 |
| `AGENT` | `node_id` | 该节点及其上进程 |
| `AGENT_GROUP` | `group_id` | 该组成员节点及其上进程 |
| `PROCESS_GROUP` | group 名字 | `spec.group` 精确相等的进程（跨节点） |

求值（入口先验，Owner / Leader 再验，与 V1.0 相同：不信任入口的「已授权」声明）：

1. 用户所有未过期 binding 的并集，不互相否定。
2. 命中任一 scope 且 role 含所需 perm → 允许。
3. 节点同时在 finance 与 prod：持有任一组成即可对该**节点**操作。对**进程**若还绑了 `PROCESS_GROUP`，必须同时满足（并集是 binding 级：一条 AGENT_GROUP 的 Operator 与一条 PROCESS_GROUP 的 Viewer 不会叠成「只能看 finance 进程」——V1.1 **不做**否定/交集策略。需要收紧就只授 `PROCESS_GROUP`，不要再授覆盖更广的 `AGENT_GROUP` / `CLUSTER`）。
4. 进程改组后，Owner 按新 spec.group 验 `PROCESS_GROUP`；旧组 binding 立即不命中。
5. 失 quorum：组/通道/binding 写全部拒绝。进程读与启停仍受 RBAC cache TTL（默认 5 分钟）约束，与 V1.0 相同。

`parseScope` 拒绝未知 type。V1.0 客户端传 `GROUP` 仍非法。

### 5.4 权限与内置角色

新增（写入 `internal/auth/perm.go` 与内置 role 种子；已有角色在 Q1 迁移里补 perm，不改用户自定义 role）：

| Perm | Super Admin | Cluster Admin | Operator | Viewer |
|------|-------------|---------------|----------|--------|
| `batch.execute` | ✓ | ✓ | ✓ | |
| `alert.read` | ✓ | ✓ | ✓ | ✓ |
| `alert.manage` | ✓ | ✓ | | |
| `backup.read` | ✓ | ✓ | | |
| `backup.manage` | ✓ | ✓ | | |

`command.execute*` 默认仍不授予除 Super Admin 外任何人，功能开关默认关。

## 6. Batch Operation

### 6.1 所有权

- 记录只存在**创建该 batch 的入口 Agent** SQLite。
- `ListBatches` / `GetBatch` 默认本机。看其他入口用 `--server` / 连那个 Agent 的 Web。
- 不进 Raft、不进 Gossip、不跨入口认领、不因入口崩溃而转移。
- 入口崩溃：已发到 Owner 的单次 mutation 仍靠 `operation_id` 幂等；该 `batch_id` 视图只在原入口磁盘（若磁盘还在，Agent 起来后可继续展示终态；未完成的 worker 重启后只恢复 `PENDING`/`RUNNING` 且尚未成功的 target，规则见 6.4）。

### 6.2 模型

本地表（逻辑字段）：

```text
batches
  batch_id        UUID
  operator
  source_agent
  type            START | STOP | RESTART | CONFIG_UPDATE
  selector_json   拍快照后的选择器
  created_at
  status          PENDING | RUNNING | COMPLETED | PARTIAL | FAILED
  summary_json    counts: success/failed/timeout/denied/conflict/unavailable/invalid

batch_targets
  batch_id
  operation_id    每个 target 独立 UUID
  node_id
  process_id      可空（纯节点级预留；V1.1 四类操作都针对进程）
  status          PENDING | RUNNING | SUCCESS | FAILED | TIMEOUT | DENIED | CONFLICT | UNAVAILABLE | INVALID
  error
  started_at
  finished_at
```

结束态（全部 target 都离开 PENDING/RUNNING 之后）：

- 全部 SUCCESS → `COMPLETED`
- 零 SUCCESS 且零 TIMEOUT → `FAILED`
- 其余（有成功也有失败，或存在 TIMEOUT）→ `PARTIAL`
- **禁止** All-or-Nothing 与跨 target 回滚
- 没有独立的 `UNKNOWN` 状态；结果未知一律 `TIMEOUT`（Case 7 的 UNKNOWN 映射到此）

零 target：创建时 `INVALID`，不插 `batches` 行。

### 6.3 展开（创建时拍快照）

| selector | 展开 |
|----------|------|
| 显式 `process_ids[]` / `(node_id, process_name)[]` | 按列表 |
| `agent_group_id` | 读本地 Raft 成员，再列出这些节点上的进程（Gossip 初筛 + Owner 确认存在） |
| `process_group` 名字 | Gossip 初筛 `summary.group`，对每个候选 RPC 读 Owner spec；`group` 不匹配则该候选 `INVALID` 并保留在结果里 |

展开之后成员变更不影响这个 batch。  
入口 RBAC 不足的 target 标 `DENIED`，仍出现在结果中。  
`CONFIG_UPDATE`：展开确认时读取该进程 `latest_revision`，作为该 target 的 `expected_revision` 写入 payload。执行时 Owner CAS；中途被别人改 → 该 target `CONFLICT`。

### 6.4 执行

- `CreateBatch` 校验 + 展开 + 落库后立即返回 `batch_id`，`status=PENDING`。
- 后台 worker：`RUNNING`，默认并发 **16**（`agent.yaml` `batch.max_concurrency`，范围 1–64）。
- 单 target 超时默认 **30s**（`batch.target_timeout`）。超时标 `TIMEOUT`（结果未知）。
- Owner 不可达：RPC 上下文超时 → `TIMEOUT`；连接拒绝 / 无路由 / 证书拒绝 → `UNAVAILABLE`。
- 每 target 走 V1.0 Write-to-Owner，header 带该 target 的 `operation_id`。
- Agent 重启：`SUCCESS`/`FAILED`/`DENIED`/`CONFLICT`/`INVALID` 不动。`PENDING`/`RUNNING` 且尚未得到终态的 target：用**原** `operation_id` 再发一次（幂等）。已标 `TIMEOUT` 的不自动重放。

Retry：

- `RetryFailed`：只挑 `FAILED` / `DENIED` / `CONFLICT` / `UNAVAILABLE` / `INVALID`，为它们生成**新** `operation_id` 再执行。
- `ReplayTimeout`：只挑 `TIMEOUT`，**复用**原 `operation_id`（调用方承认结果未知，要的是去重而不是二次执行）。
- `SUCCESS` 永不重放。

需要 `batch.execute`，外加每个 target 对应的 `process.start|stop|restart` 或 `process.config.update`。入口写一条 batch audit；Owner 写各自 execution audit。

Case 7：部分节点 offline → `PARTIAL`；TIMEOUT 必须出现在 summary 与 UI，禁止改成 SUCCESS 或从列表消失。

### 6.5 不做

- 全局 Batch 总线、把进度 gossip 出去
- 跨节点启动顺序 / 跨节点依赖
- 任意命令的 batch（`command.execute.batch` 仍关）

## 7. Alert 与通道

### 7.1 配置（Raft）

```text
AlertChannel
  channel_id     UUID
  type           WEB | WEBHOOK | EMAIL | WECOM | DINGTALK | SLACK
  name
  enabled        bool
  config_json    按 type：URL/headers/SMTP/secret 等
  created_unix
  updated_unix

AlertPolicy
  dedup_window           默认 10m
  notify_on_resolve      默认 true
  cpu_high_percent       默认 90
  memory_high_percent    默认 90
  disk_high_percent      默认 90
  high_consecutive_mins  默认 2
  suspect_too_long       默认 2m
```

CRUD 需 `alert.manage`。通道 secret/password 存于 Raft，API 只回显非密钥字段（URL/host 保留，secret 永不回传）。

alert **行必写**发送者 SQLite，与是否配置外发通道无关。`type=WEB` 无需外部 config，也不调用网络 `Send`。`WEBHOOK`/`EMAIL`/`WECOM`/`DINGTALK`/`SLACK` 在 `enabled=true` 时 `Send`。没有外发通道时 inbox 仍可用。

### 7.2 发送者

| 类型 | fingerprint | 发送者 | 默认 severity |
|------|-------------|--------|---------------|
| `PROCESS_EXIT` | `PROCESS_EXIT:{process_id}` | Owner | WARNING |
| `PROCESS_FATAL` | `PROCESS_FATAL:{process_id}` | Owner | CRITICAL |
| `PROCESS_CRASH_LOOP` | `PROCESS_CRASH_LOOP:{process_id}` | Owner | CRITICAL |
| `HEALTH_FAILED` | `HEALTH_FAILED:{process_id}` | Owner | WARNING |
| `CPU_HIGH` / `MEMORY_HIGH` | `{TYPE}:{process_id}` 或节点级 `{TYPE}:{node_id}` | Owner / 本机 | WARNING |
| `DISK_HIGH` | `DISK_HIGH:{node_id}` | 本机 | WARNING |
| `LOCAL_DB_ERROR` | `LOCAL_DB_ERROR:{node_id}` | 本机 | CRITICAL |
| `AGENT_FAILED` | `NODE_FAILED:{node_id}` | Leader | CRITICAL |
| `AGENT_SUSPECT_TOO_LONG` | `NODE_SUSPECT:{node_id}` | Leader | WARNING |
| `CONTROL_NO_QUORUM` | `CONTROL_NO_QUORUM:{cluster_id}` | 见下方 | CRITICAL |
| `CERT_EXPIRING` | `CERT_EXPIRING:{node_id}` | Leader | WARNING |
| `VERSION_MISMATCH` | `VERSION_MISMATCH:{node_id}` | Leader | WARNING |

进程/本机：Owner 或本机单写者。  
集群级（Failed / Suspect / Cert / Version）：仅 **当时 Raft Leader** 调用外发 `Send`。Leader 切换后新 Leader 本地若无该 fingerprint 记录，允许再发一条（窗口内可能双发，PRD 允许）。失 quorum 时这四类停发。

`CONTROL_NO_QUORUM`：任一 **voter** 在连续 `suspect_too_long` 内看不到 Leader 时，本机写 FIRING 并允许 `Send`。fingerprint 集群唯一，仅本机去重，故最多 N(voter) 条外发。不承诺 exactly once。非 voter 不发此类。

`CERT_EXPIRING`：节点证书 `NotAfter - now ≤ 30d`。  
`VERSION_MISMATCH`：ALIVE 成员的 `protocol_version` 不在 `{0, 1}`（0 视为 1）。V1.0/V1.1 混跑（均为协议 1）不触发。

V1.1 **无**手动 Ack。状态只有 `FIRING` 与 `RESOLVED`。对端恢复 / HEALTHY / 节点重新 ALIVE 时发 RESOLVED，是否外发看 `notify_on_resolve`。

阈值类用 **1 分钟历史点**（没有点则退回即时快照），连续 `high_consecutive_mins` 分钟超阈值才 FIRING，避免 5 秒抖。

### 7.3 实例（发送者 SQLite）

```text
alerts
  alert_id
  fingerprint
  type
  severity        WARNING | CRITICAL
  node_id
  process_id      可空
  payload_json
  state           FIRING | RESOLVED
  first_at
  last_at
  notified_at
  resolved_at
```

同一发送者、同一 fingerprint **复用一行**：更新 `last_at`；state 拉回 `FIRING`；仅当 `now - notified_at >= dedup_window`（或从未成功 Send）才再次 `Send` 并刷新 `notified_at`。不因每次触发新建 `alert_id`。

### 7.4 通道实现

接口：`Send(ctx, alert) error`。V1.1 全部验收：

| type | 行为 |
|------|------|
| WEB | 无外部 I/O；inbox 即表 |
| WEBHOOK | HTTP POST JSON；`config_json` 可含静态 headers；若设 `hmac_secret` 则带 `X-ProcMesh-Signature`（HMAC-SHA256 hex） |
| EMAIL | SMTP（STARTTLS 若配置） |
| WECOM | 企业微信群机器人 webhook |
| DINGTALK | 钉钉自定义机器人（含加签） |
| SLACK | Incoming webhook |

发送在发送者进程内：同步尝试，最多 3 次指数退避，仍失败写 audit + 行内错误字段，**不**把投递状态写入 Raft。

### 7.5 读路径

`ListAlerts`：本机 ∪ 对其他 ALIVE 节点按需 RPC，缺失/超时标 STALE。Overview Recent Alerts 同一聚合。禁止把 STALE 画成「当前无告警」。需 `alert.read`。

### 7.6 不做

- 观察者抢发、Raft fingerprint 锁
- 按 Agent Group 拆通道
- 值班表、静默日历、Exactly Once

## 8. Historical Metrics

### 8.1 序列与分辨率

只存 V1.0 Collector 已有 5 条：

- 节点：`cpu_percent`、`memory_percent`、`disk_percent`
- 进程：`cpu_percent`、`memory_bytes`

不采集 Network / Load / FD / IO。

Collector 仍 5 秒刷新即时缓存。每分钟把该分钟内样本聚成一点写入本地：

| 层 | 分辨率 | 保留 | 聚合 |
|----|--------|------|------|
| raw_min | 1 分钟 | 24 小时 | CPU/Mem 均值；Disk **窗口最大**百分比 |
| down_5m | 5 分钟 | 第 1 天之后到第 7 天 | 同上（对 1 分钟点再聚合） |

满窗删最老。进程消失后其序列不再写新点，旧点按 TTL 删。`-1` / 采集失败的分钟不写点（查询表现为缺口，不插 0）。

存储：Owner 现有 SQLite **同库新表** `metric_samples`。`>95%` 磁盘停写历史；`>90%` 先删 `down_5m` 最老行。不进 Raft、不进 Gossip。

### 8.2 读

`MetricsService.GetNodeHistory` / `GetProcessHistory`：`node_id` / `process_id`、时间范围。`resolution` 省略时：range ≤ 24h 用 1 分钟层，否则用 5 分钟层。非 Owner 入口 RPC 到 Owner。不可达 → `UNAVAILABLE`，UI STALE，**禁止**用 Gossip 摘要冒充曲线。

Dashboard：节点/进程详情趋势图用此 API。Overview 计数与资源百分比仍用 Gossip 即时摘要。

## 9. Configuration Backup / Restore

### 9.1 备份对象

只含 Owner 上每个进程的 **spec + `config_revisions` 全历史**。不含 runtime、PID、logs、metrics、audit、Raft、证书私钥、业务数据。

快照元数据：

```text
snapshot_id, cluster_id, node_id, created_at, process_ids[],
revision_range per process, sha256, sink, location
```

### 9.2 Sink

接口：`Put` / `List` / `Get` / `Delete`。

| sink | 位置 | 传输 |
|------|------|------|
| `fs` | 默认 `$data_dir/backup/fs/`，可配 | 本地文件 0600 |
| `s3` | `agent.yaml` 的 `backup.s3`（endpoint / bucket / prefix / 凭据）。S3 密钥不进 Raft、不进 API 回显 | HTTPS |
| `peer` | 调用方指定 `target_node_ids[]`；对端 `$data_dir/backup/peer/<source_node_id>/<snapshot_id>` | mTLS RPC，对端只落盘，**禁止 apply** |

触发：手动 `CreateBackup`；可选本机定时（默认关，`backup.schedule` cron 表达式）。  
Peer 目标必须是当前 ADMITTED 成员。被 remove 的节点上的副本不自动搬迁。

S3 凭据只来自本机环境变量 / `agent.yaml`，API 不回传。

### 9.3 Restore

- 只许针对**当前该进程的 Owner**。
- 唯一写路径：`Manager.ApplySpec`，产生**新 revision**，要求调用方提供 `expected_revision`。
- 禁止：把 snapshot 直写 `process_specs` 表；restore 到非 Owner；在本机用 Peer 文件「重建别人的进程」。
- 可一次多进程；每进程独立 CAS，部分 `CONFLICT` 允许。
- 分区期间不得拿旧备份覆盖仍活着的 Owner。

权限：`backup.read` 列表/下载元数据与快照；`backup.manage` 创建/删除/restore。

List：本机 index ∪ 按需问已配 S3 / 指定 Peer，失败 STALE，不得显示成「没有备份」。

### 9.4 不做

- 集群一键 DR、Raft 快照外发、跨 cluster import
- 备份载荷额外加密层
- 对端扫描 `backup/peer` 后自动 adopt

## 11. 错误处理

沿用 V1.0 错误码：

| 场景 | 码 |
|------|-----|
| 空 batch selector、非法 group 名、未知 sink、非法 scope | `INVALID` |
| restore / config batch / 删仍被 binding 引用的组 | `CONFLICT` |
| Owner / Peer / S3 / 旧节点缺 RPC | `UNAVAILABLE` |
| 单 target 或聚合超时 | `TIMEOUT` |
| RBAC 未命中 | `DENIED` |
| 失 quorum 时组/通道/binding 写 | `UNAVAILABLE` |
| 磁盘 95% 停写历史/备份 | `DEGRADED`（读尽量继续） |

TIMEOUT 表示未知，不是 FAILED。UI 与 Case 7 必须单独暴露。

磁盘保护阈值与 V1.0 `disk` 配置相同。Local DB 损坏：DEGRADED，停高风险写，不杀业务进程；本机可发 `LOCAL_DB_ERROR`。

网络分区：两侧本地进程继续；禁止用 Peer 备份在本机创建对端进程；愈合后不得用旧备份或 STALE Gossip 覆盖 Owner 权威 spec。

| 包 | 最低 |
|----|------|
| `internal/control` | 80%（含 group/channel FSM） |
| `internal/auth` | 80%（含新 scope） |
| `internal/batch` | 80% |

| `internal/metrics` | 历史读写与降采样必须有测试 |

| `web/` | Vitest + Playwright：组授权、batch 部分成功、告警 STALE、restore 409 |

必须脚本化：

1. **Case 7**：多 target 中途部分不可达 → `PARTIAL`，TIMEOUT 可见。
2. 入口崩溃再恢复：成功 target 不因重放再执行；`operation_id` 幂等。
3. Leader 切换：同 fingerprint 在 `dedup_window` 内不保证 0 条重复，但测试应断言「不是每个 follower 都外发」（集群级只有 Leader 调 `Send`）。
4. Restore 错误 `expected_revision` → `CONFLICT`，store 未被 snapshot 直写。
5. 失 quorum：不能 `group_put` / `PutChannel`；Owner 仍可写进程告警 inbox。
6. 分区：Peer `Put` 到对端只产生文件；对端 process 列表不出现源节点的进程。
7. `PROCESS_GROUP`：改 spec.group 后旧 binding 立刻 DENIED。
8. 删 Agent Group：仍有 binding 时 `CONFLICT`。

macOS CI：单测 + 不依赖 cgroup / 真 S3 / 真 SMTP 的集成。S3 与外发通道用 fake server。Linux CI 跑完整验收。

## 15. 实施禁止事项

V1.0 §18 全部继续有效，并增加：

- 把 Process Group 做成 Raft 注册表，或用 Gossip 当组成员权威
- 把 batch 进度、alert 实例、历史点、backup 载荷写入 Raft 或当作 Gossip 事务
- 入口崩溃后在另一节点「接管」同一 `batch_id` 并重放已 SUCCESS 的 target
- 非 Leader 发送 `AGENT_FAILED` / `CERT_EXPIRING` / `VERSION_MISMATCH` / `AGENT_SUSPECT_TOO_LONG`
- 用 Peer/FS/S3 快照绕过 `ApplySpec` 写 store
- 因对端 FAILED，在本机 restore 出对端的进程
- 把 STALE、TIMEOUT、UNKNOWN 画成成功或「无告警」
- 无 `operation_id` 的 batch/backup/restore/通道写
- 无 `expected_revision` 的 restore 与 config batch
- 打开 `command.execute.batch` 默认值

## 16. Key Decisions

1. **Process Group 不是控制面对象** — 权威留在 Owner spec，符合 Local Authority，也符合 PRD §12 未列出 `process_groups`。
2. **Agent Group 显式成员、可重叠** — RBAC 与 batch 选节点可审计；不用 label selector，避免授权边界随 Gossip 抖动。
3. **Batch 归入口本地** — 操作流水不进 Raft；任意节点可当入口；换入口就看不到任务（文案写明）。
4. **Alert 双发送者** — Owner / Leader 单写者去重，避免 N 节点同时打 Webhook；不承诺 exactly once。
5. **读模型复用 V1.0** — Raft 本地读控制面；其余按需 RPC + STALE。拒绝「把目录塞进 Gossip/Raft 索引」。
6. **历史只存已有 5 序列、7 天两层** — 先把存储/查询/磁盘保护做对，不顺手扩采集面。
7. **三 Sink 都进 V1.1，restore 只走 ApplySpec** — 满足 §38/§89，同时钉死 Single Writer。
8. **Protocol 仍为 1** — 字段加法；混跑时新 RPC 对旧节点逐调用失败，不整群驱逐。
